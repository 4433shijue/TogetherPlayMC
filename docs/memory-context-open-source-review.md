# TogetherPlayMC 记忆与上下文开源方案调研

核对日期：2026-11-18。本文是方案评估，尚未接入以下依赖，也没有把个人聊天发送到这些服务。项目能力以本次 v0.14.0 源码为准；开源项目以链接中的官方仓库和文档为准。

后续进展：v0.15.0 已在本机接入 Transformers.js 与多语言 MiniLM，并实现分层上下文和带来源校验的增量原话整理。下文保留调研时的 v0.14.0 基线；完整记忆引擎仍未接入。

## 当前基础与缺口

我们已有角色、世界和维度隔离，固定记忆，来源证据，待确认修正与修改历史，约定与待续话题，聊天原文回查，以及每轮真实请求上下文的查看入口。

目前的记忆召回主要依靠词语匹配。`src/memory-continuity.mjs` 可以查到较早聊天，但换一种说法时仍可能漏掉。`src/companion-plus.mjs` 的历史整理保留消息编号和原话节选，本质是有长度上限的摘录，不是理解语义的摘要。`boundInput` 以字符预算裁掉较早完整回合，不能自动判断哪些情绪、约定和事实更值得留下。

因此，最值得补的是语义召回、带证据的经历整理、时间变化、按重要性安排上下文。已存在的编辑、确认、回退和透明诊断应继续作为入口。

## 候选比较

| 项目 | 官方提供的能力 | 在我们这里可怎么用 | 接入判断 |
| --- | --- | --- | --- |
| [Hindsight](https://github.com/vectorize-io/hindsight) · MIT | retain / recall / reflect；区分世界事实、经历、归纳观察和心智模型；语义、关键词、图关系、时间四路检索 | 把“我们一起做过什么”与“他逐渐了解了你什么”分开；后者保持推测标签和原始证据 | 完整记忆引擎的优先试验对象。有 Node 客户端，但后端仍需要独立运行，存储为 PostgreSQL/pgvector 等；Windows 和嵌入式数据库有官方支持，不能直接当成一个轻量 npm 包打进现有应用 |
| [Mem0](https://github.com/mem0ai/mem0) · Apache-2.0 | 用户、会话和 Agent 记忆；提取与检索；Python/npm 接入；本地库、自部署和云服务几种形态 | 更快补齐“不同说法也能想起同一件事”，作为语义记忆的对照方案 | 值得与 Hindsight 比较。需要配置提取模型与 embedding；开源库、自部署与云平台功能不同，不能把云端展示都算作本地能力。当前增强检索示例使用英语 spaCy 模型，中文效果须单独验证 |
| [Graphiti](https://github.com/getzep/graphiti) · Apache-2.0 | 事实有效时间、历史失效关系、来源事件；语义、关键词、关系联合检索 | 记录“以前住海边，后来搬到森林”；能回答现在住哪，也保留过去的共同经历 | 先借鉴时间字段和关系设计。完整接入需要 Python 及图存储，抽取依赖模型结构化输出；相对现有 Node/SQLite 发行包增加维护成本 |
| [Letta 当前代码](https://github.com/letta-ai/letta-code) · Apache-2.0 | 长期身份、可编辑记忆、历史搜索、MemFS、后台 dreaming | 少量核心身份常驻；较大的共同经历按需读取；在闲时整理记忆 | 优先借鉴上下文分层和后台整理。Letta 是完整 Agent 运行框架，直接替换会涉及现有工具、请求追踪和权限。旧 letta 仓库明确把 V1 服务归档，不能沿用旧安装文章判断现状 |
| [LangMem](https://github.com/langchain-ai/langmem) · MIT | 后台记忆提取、整理；可搭配不同存储；增量对话摘要 | 原文完整保留；只对新增旧回合做摘要，保留最近完整聊天，避免同一内容反复压缩 | 优先借鉴流程。当前是 Python 库，我们可以在 Node 中实现等价的分层流程，也可另建适配服务做效果对照 |
| [LLMLingua](https://github.com/microsoft/LLMLingua) · MIT | 基于模型的提示词压缩；可指定某些段落不压缩 | 未来压缩很长的攻略资料或重复工具结果 | 后置。压缩本身需要模型运行资源；中文情绪、否定词、坐标和承诺必须检查保真，不能套用论文压缩倍数承诺本项目收益 |

补充核对：[Acontext](https://github.com/memodb-io/Acontext) 仓库现已声明停止维护。它的可读文件记忆、按需读取值得参考，但不建议成为新核心依赖。

## 推荐组合

先借鉴 Letta 的常驻/按需上下文分层，加上 LangMem 的增量摘要流程；再把 Hindsight 与 Mem0 放到同一套中文场景里做比较。Graphiti 的时间关系可以先用本地 SQLite 表表达，等关系查询的价值被验证后再考虑完整图服务。

不要同时接入多套记忆系统。SQLite 继续保存原始聊天和玩家确认的事实；外部索引只是可删除、可重建的派生数据。角色、世界、维度、用户身份都由服务端强制过滤，不能依靠模型自己记得隔离。

建议新增统一记忆接口，集中负责查询、候选提取、确认、删除和重建。当前工具 `remember` 与 `recall_chat` 接这个接口；检索结果仍带原文 ID、时间、可信状态和命中原因。模型提议与用户确认的事实保持不同权重。删除原文或记忆时，同时删除向量、摘要和其他派生索引。

上下文每轮分四层：

1. 固定角色与核心关系，小而稳定，玩家修改后才变化。
2. 当前会话与未完事项，保留最近完整回合和仍有效的约定。
3. 本轮相关的历史证据，结合语义、关键词、时间和世界范围检索，去重后按预算选取。
4. 当前游戏状态、查询资料、工具结果与玩家这句话。只放本轮需要的字段，避免旧状态被当成现在。

摘要在空闲时或达到阈值时增量生成，记录覆盖到的消息编号、模型版本和来源。摘要失败时继续使用原文节选。不能把“想建房子”“建议去矿洞”整理成“已经建好”“已经去过”。原始聊天不因摘要而删除。

## 值得先做的验证

用同一组本地中文数据，比较现有基线、轻量分层方案、Hindsight、Mem0，先离线检查检索，真实模型质量测试另行预算。至少覆盖这些情况：

- 说“之前想住的那种地方”时，能否找回很早说过的樱花林，而不要求关键词完全重合。
- 偏好先海边后森林；更正后答当前偏好，回忆过去时还能说清变化。
- 两个世界都有“小屋”，坐标和经历不能串；两个角色的私人聊天不能串。
- 约定跨几次游戏后仍可接上，已经取消或完成的约定不再当作未办事项。
- 情绪性表达、玩笑、假设、转述与明确事实分开，不把一次低落永久写成人格判断。
- 删除、恢复备份、切换 embedding 模型后，旧索引不会残留或混用。
- 长攻略与多轮工具调用后，关键原话、否定词、坐标仍保留，工具调用和结果保持成对。

指标同时看召回质量、错误记忆、跨世界串记忆、证据可追溯、首字延迟、额外模型/embedding 调用、磁盘和内存开销。字符统计仍用于诊断；计费 token 与缓存命中必须以供应商 usage 为准。不会从开源项目的英文 benchmark 直接推断中文陪伴效果。

本轮结论是架构与候选选择，尚未实测它们对本项目中文对话的提升，也未加入自动记忆整理的额外模型开销。
